## Notas específicas deste app

- Constantes que precisam ser lidas tanto por um Client Component (`app/page.tsx`) quanto por um módulo Server-only com `node:sqlite`/`node:fs` (`lib/historico.ts`, `lib/store.ts`) devem morar num arquivo à parte sem imports `node:*` (ex.: `lib/sensivel.ts`, `lib/formato.ts`), reexportado pelo módulo Server-only. Importar direto de um módulo com `node:sqlite` a partir de um `"use client"` quebra o bundle do cliente.
- `eslint-plugin-react-hooks@7` (a versão usada por `eslint-config-next` aqui) não analisa estabilidade de forma transitiva: uma função do componente (ex.: `gerar`) que chama outra função também do componente (ex.: `carregarHistorico`) passa a ser tratada como "instável" pelo `react-hooks/exhaustive-deps`, mesmo que ambas só usem setters de `useState`/`fetch`. Se isso acontecer num `useEffect` com array de dependências vazio, prefira inline a chamada em vez de extrair para uma função irmã (este projeto não usa `useCallback`).
- `.btn-primary` (globals.css) já vem com `w-full` embutido (pensado para botões de submit isolados). Ao colocar um `.btn-primary` ao lado de outro botão no mesmo flex row (ex.: `Entregar`), cancele com `!w-auto` (mesmo padrão já usado em `components/setup.tsx`) e controle a largura via `flex-1`/`shrink-0` no container.
- Para capturas headless (`chromium --headless --screenshot`) do estado "pronto" (`<article className="reveal">`), `--run-all-compositor-stages-before-draw` nem sempre basta: `--virtual-time-budget` é tempo virtual de timers JS, não tempo real de compositor, e a transição CSS de 0,45s pode não ter "tempo real" suficiente para terminar. Adicionar `--force-prefers-reduced-motion` desliga `.reveal` de forma determinística (via `@media (prefers-reduced-motion: reduce)` em `globals.css`) e resolve a captura "desbotada".
- `Entregar` (`components/ui.tsx`) usava `location.origin` direto no corpo da função para montar o link de `/r/[id]`. Como esse componente é renderizado por Server Components (`app/r/[id]/page.tsx`, `app/imprimir/[id]/page.tsx`), isso quebrava com `ReferenceError: location is not defined` (`location`/`window` só existem no browser) — bug descoberto e corrigido só na US-017 (replicação para `agente-kanban`), porque nenhuma verificação anterior tinha carregado `/r/[id]` de um resultado com `id`. Corrigido com `id && typeof window !== "undefined" ? ... : undefined`. Ao criar qualquer novo componente client-only que leia `location`/`window` fora de um `useEffect`/handler, aplicar a mesma guarda.
- Um campo "pré-preenchido do setup" que não é uma chave de nenhuma `Integracao` (ex.: `NOME_USUARIO`, US-021) não precisa passar por `PUT /api/setup` nem por uma `Integracao` fake em `lib/integracoes.ts`: a própria rota da feature (`app/api/pdi/route.ts`) pode ler com `getConfig("NOME_USUARIO")` no `GET` e gravar com `setConfig("NOME_USUARIO", valor)` no `POST` quando o campo vier preenchido, usando o mesmo `lib/store.ts` das integrações. Assim o campo se "lembra" sozinho a partir do segundo uso, sem exigir configuração manual em `/setup`.
- (US-046) Endpoint MCP (`app/mcp/route.ts` + `lib/mcp.ts`): JSON-RPC 2.0 implementado à mão (sem `@modelcontextprotocol/sdk`, decisão registrada no README). O código de acesso é gerado por `lib/mcp.ts` e guardado em `lib/store.ts` sob a chave `MCP_CODIGO_ACESSO` (mesmo mecanismo de `getConfig`/`setConfig` das integrações). A lógica de cada funcionalidade que vira ferramenta MCP deve morar num arquivo próprio (aqui, `lib/pdi.ts`, extraído de `app/api/pdi/route.ts`) para que a rota HTTP normal e `lib/ferramentas.ts` (a lista de ferramentas do MCP) chamem a mesma função, sem duplicar prompt nem gravação no histórico.
- (US-046) `scripts/verificar-jargao.mjs` varre todo `components/*.tsx` (exceto `setup.tsx`) — um cartão novo de `/setup` como `components/AcessoMCP.tsx` **é** varrido, mesmo não sendo a tela principal. A palavra "token" (um dos termos proibidos) não pode aparecer como texto visível nem em atributos não filtrados pelo script (`title`, `aria-label`, `placeholder` não estão na lista de atributos técnicos ignorados pelo script); por isso a UI usa "código de acesso" em vez de "token" em todo lugar visível — a variável interna pode se chamar `token`/`codigo`, só o texto renderizado importa.
- (US-047) Um valor `typeof window !== "undefined" ? real : fallback` calculado direto no corpo do componente só é seguro quando nunca é renderizado como texto/atributo visível na primeira passada (ex.: `link` em `Entregar`/`components/ui.tsx`, usado só dentro de `onClick` e dentro de um menu que começa fechado). Quando o valor aparece direto em texto (era o caso de `endereco` em `components/AcessoMCP.tsx`, renderizado em `<code>{endereco}</code>`), o mesmo padrão causa hydration mismatch de verdade (log do `next dev` mostra "Hydration failed..."). Corrija inicializando o estado com o valor seguro para SSR (ex.: `"/mcp"`) e atualizando dentro de um `useEffect` — encaixe a atualização dentro do `.then()` de uma promise que o efeito já dispara (ex.: o mesmo `fetch(...).then(...)` que já existia), em vez de uma chamada solta de `setState` direto no corpo do efeito, porque `react-hooks/set-state-in-effect` acusa erro nesse segundo caso.
- **Limitação conhecida, não resolvida (investigada na US-020, replicação para `prospeccao-ia`):** quando `DataTable` tem mais linhas do que cabem numa página A4 impressa, `chromium --headless --print-to-pdf` em `/imprimir/[id]` pagina errado — cada linha do cartão mobile (`.card` com `divide-y`, que é o formato usado no print porque a largura útil do A4 cai abaixo do breakpoint `md`) sai numa página quase inteiramente em branco, em vez de várias linhas por página. Tentei corrigir isolando `break-inside: avoid` só nas linhas (`.datatable-linha`) e `break-inside: auto` no container (`.datatable-linhas`), inclusive com `!important`, e o resultado do PDF não mudou nem um byte relevante — depois testei `break-inside: auto !important` em `.card` inteiro (removendo o "avoid" da equação por completo) e o bug persistiu idêntico, e até aumentando o `@page` para 2000mm de altura o conteúdo continuou paginando a cada poucas linhas. Ou seja, a causa não é `break-inside`; é algo mais profundo na interação entre `@page` nomeada (`page: folha-impressao`) e o layout do cartão mobile que ainda não foi identificado. Revertido para o estado original (sem o "fix"). Antes de mexer em `DataTable` para uma tabela com muitas linhas dentro de `/imprimir/[id]`, tratar isso como um problema em aberto, não como algo já resolvido.
