@AGENTS.md

## Notas específicas deste app

- Constantes que precisam ser lidas tanto por um Client Component (`app/page.tsx`) quanto por um módulo Server-only com `node:sqlite`/`node:fs` (`lib/historico.ts`, `lib/store.ts`) devem morar num arquivo à parte sem imports `node:*` (ex.: `lib/sensivel.ts`, `lib/formato.ts`), reexportado pelo módulo Server-only. Importar direto de um módulo com `node:sqlite` a partir de um `"use client"` quebra o bundle do cliente.
- `eslint-plugin-react-hooks@7` (a versão usada por `eslint-config-next` aqui) não analisa estabilidade de forma transitiva: uma função do componente (ex.: `gerar`) que chama outra função também do componente (ex.: `carregarHistorico`) passa a ser tratada como "instável" pelo `react-hooks/exhaustive-deps`, mesmo que ambas só usem setters de `useState`/`fetch`. Se isso acontecer num `useEffect` com array de dependências vazio, prefira inline a chamada em vez de extrair para uma função irmã (este projeto não usa `useCallback`).
- `.btn-primary` (globals.css) já vem com `w-full` embutido (pensado para botões de submit isolados). Ao colocar um `.btn-primary` ao lado de outro botão no mesmo flex row (ex.: `Entregar`), cancele com `!w-auto` (mesmo padrão já usado em `components/setup.tsx`) e controle a largura via `flex-1`/`shrink-0` no container.
- Para capturas headless (`chromium --headless --screenshot`) do estado "pronto" (`<article className="reveal">`), `--run-all-compositor-stages-before-draw` nem sempre basta: `--virtual-time-budget` é tempo virtual de timers JS, não tempo real de compositor, e a transição CSS de 0,45s pode não ter "tempo real" suficiente para terminar. Adicionar `--force-prefers-reduced-motion` desliga `.reveal` de forma determinística (via `@media (prefers-reduced-motion: reduce)` em `globals.css`) e resolve a captura "desbotada".
- `Entregar` (`components/ui.tsx`) usava `location.origin` direto no corpo da função para montar o link de `/r/[id]`. Como esse componente é renderizado por Server Components (`app/r/[id]/page.tsx`, `app/imprimir/[id]/page.tsx`), isso quebrava com `ReferenceError: location is not defined` (`location`/`window` só existem no browser) — bug descoberto e corrigido só na US-017 (replicação para `agente-kanban`), porque nenhuma verificação anterior tinha carregado `/r/[id]` de um resultado com `id`. Corrigido com `id && typeof window !== "undefined" ? ... : undefined`. Ao criar qualquer novo componente client-only que leia `location`/`window` fora de um `useEffect`/handler, aplicar a mesma guarda.
- Um campo "pré-preenchido do setup" que não é uma chave de nenhuma `Integracao` (ex.: `NOME_USUARIO`, US-021) não precisa passar por `PUT /api/setup` nem por uma `Integracao` fake em `lib/integracoes.ts`: a própria rota da feature (`app/api/pdi/route.ts`) pode ler com `getConfig("NOME_USUARIO")` no `GET` e gravar com `setConfig("NOME_USUARIO", valor)` no `POST` quando o campo vier preenchido, usando o mesmo `lib/store.ts` das integrações. Assim o campo se "lembra" sozinho a partir do segundo uso, sem exigir configuração manual em `/setup`.
- (US-046) Endpoint MCP (`app/mcp/route.ts` + `lib/mcp.ts`): JSON-RPC 2.0 implementado à mão (sem `@modelcontextprotocol/sdk`, decisão registrada no README). O código de acesso é gerado por `lib/mcp.ts` e guardado em `lib/store.ts` sob a chave `MCP_CODIGO_ACESSO` (mesmo mecanismo de `getConfig`/`setConfig` das integrações). A lógica de cada funcionalidade que vira ferramenta MCP deve morar num arquivo próprio (aqui, `lib/pdi.ts`, extraído de `app/api/pdi/route.ts`) para que a rota HTTP normal e `lib/ferramentas.ts` (a lista de ferramentas do MCP) chamem a mesma função, sem duplicar prompt nem gravação no histórico.
- (US-046) `scripts/verificar-jargao.mjs` varre todo `components/*.tsx` (exceto `setup.tsx`) — um cartão novo de `/setup` como `components/AcessoMCP.tsx` **é** varrido, mesmo não sendo a tela principal. A palavra "token" (um dos termos proibidos) não pode aparecer como texto visível nem em atributos não filtrados pelo script (`title`, `aria-label`, `placeholder` não estão na lista de atributos técnicos ignorados pelo script); por isso a UI usa "código de acesso" em vez de "token" em todo lugar visível — a variável interna pode se chamar `token`/`codigo`, só o texto renderizado importa.
- (US-048) `app/mcp/route.ts` importa `NOME_SERVIDOR` de `@/lib/ferramentas` (não é mais uma constante local do arquivo): como `scripts/verificar-padrao.sh` passou a comparar `lib/mcp.ts` e `app/mcp` byte a byte entre os apps (ver US-048), o nome do servidor MCP (que é específico de cada app) precisava sair de `route.ts` para um arquivo já próprio de cada app (`lib/ferramentas.ts`, nunca comparado) — assim `app/mcp/route.ts` fica idêntico em todos os apps e pode ser copiado sem alteração, igual a `lib/mcp.ts`.
- (US-047) Um valor `typeof window !== "undefined" ? real : fallback` calculado direto no corpo do componente só é seguro quando nunca é renderizado como texto/atributo visível na primeira passada (ex.: `link` em `Entregar`/`components/ui.tsx`, usado só dentro de `onClick` e dentro de um menu que começa fechado). Quando o valor aparece direto em texto (era o caso de `endereco` em `components/AcessoMCP.tsx`, renderizado em `<code>{endereco}</code>`), o mesmo padrão causa hydration mismatch de verdade (log do `next dev` mostra "Hydration failed..."). Corrija inicializando o estado com o valor seguro para SSR (ex.: `"/mcp"`) e atualizando dentro de um `useEffect` — encaixe a atualização dentro do `.then()` de uma promise que o efeito já dispara (ex.: o mesmo `fetch(...).then(...)` que já existia), em vez de uma chamada solta de `setState` direto no corpo do efeito, porque `react-hooks/set-state-in-effect` acusa erro nesse segundo caso.
- (US-051) Next.js 16 neste projeto renomeou `middleware.ts` para `proxy.ts` (mesma API, `export function proxy(...)`; `middleware.ts` ainda funciona mas `next build` avisa "deprecated"): use `proxy.ts` em qualquer novo arquivo desse tipo, nunca `middleware.ts`. Também: `response.headers.set("Cache-Control", ...)` dentro de `proxy.ts` é sobrescrito pelo dev server (Turbopack) para uma página (`app/f/[token]/page.tsx`, "no-cache, must-revalidate" no lugar de "no-store") mas funciona corretamente em `npm run build && npm run start` — verificar headers de página sempre em build de produção, não em `next dev`; numa rota (`route.ts`) o header setado direto no `NextResponse.json(...)` não tem esse problema em nenhum dos dois modos.
- (US-051) `eslint-plugin-react-hooks@7`, regra `react-hooks/purity`: um Server Component (função exportada que devolve JSX, mesmo sem `"use client"`) não pode chamar `Date.now()` (nem qualquer função "impura" da lista da regra) diretamente no corpo da função — dá erro de lint ("Cannot call impure function during render"), mesmo em `app/f/[token]/page.tsx`, que só roda no servidor. Curiosamente `new Date()` (o construtor) não é pego pela mesma regra (`app/imprimir/[id]/page.tsx` já usa `data(new Date())` inline sem acusar nada). Ao precisar comparar uma data de expiração com "agora" dentro de um componente, mova a comparação para uma função exportada de um `lib/*.ts` (ex.: `expirou()` em `lib/formularios.ts`) e chame essa função a partir do componente, em vez de `Date.now()`/`.getTime()` inline no JSX/corpo do componente.
- (US-051) Novo par de tabelas `formularios`/`respostas` em `lib/formularios.ts` (mesmo arquivo SQLite de `lib/store.ts`/`lib/historico.ts`, mesmo padrão de `criar`/`obter`/`apagar` com id/token via `crypto.randomBytes(...).toString("base64url")`): a tela pública (`app/f/[token]/page.tsx` + `FormularioPublico.tsx`) é 100% genérica — nunca referencia o nome do app ou o `tipo` do formulário, só o que está em `formulario.parametros` (`marca`, `nome`, `titulo`, `descricao?`) e `formulario.campos`. Quem grava algo "de marca" (nome do app, textos) é sempre o app no momento de `criar(...)`, nunca o arquivo compartilhado. O callback que transforma uma resposta em resultado (`registrarCallback`/`obterCallback`, por `tipo`) também mora em `lib/formularios.ts` (genérico), mas quem *chama* `registrarCallback` é sempre um módulo próprio do app (ex.: futuramente `lib/pdi.ts`); por isso `app/api/f/[token]/route.ts` (ao contrário de `lib/formularios.ts` e `app/f/[token]/page.tsx`) não é copiado sem alterar entre apps — é o único ponto que pode precisar importar o módulo certo do app para garantir que o callback já esteja registrado.
- (US-052) Um diálogo modal (overlay) que precisa nascer com estado limpo a cada abertura (ex.: `DialogoAutoavaliacao`, aberto por um botão do painel) não deve ficar sempre montado com uma prop `aberto` + um `useEffect` que reseta os `useState` quando `aberto` vira `true` — isso é `setState` síncrono dentro de um efeito e a regra `react-hooks/set-state-in-effect` (mesmo pacote `eslint-plugin-react-hooks@7` já registrado acima) acusa erro. Em vez disso, o componente pai só monta o diálogo condicionalmente (`{aberto && <Dialogo ... />}`), e o próprio componente do diálogo não recebe mais a prop `aberto`: como ele nasce e morre a cada abertura/fechamento, os `useState(valorInicial)` já começam limpos sem precisar de nenhum efeito de reset.
- (US-052) `lib/formularios.ts` ganhou `listarRespostasPorTipo(tipo, limite)` (SQL `JOIN` entre `respostas` e `formularios`, filtrando por `tipo`): necessário sempre que um mesmo `tipo` de formulário gera **vários** links/convites ao longo do tempo (ex.: "Pedir autoavaliação por link" cria um link novo por colaborador, com `limite: 1`), e a tela precisa agregar todas as respostas recebidas independente de qual link/`token` cada uma veio — `listarRespostas(token)` (já existia) só serve para um único link. Ao registrar o `registrarCallback` de um novo `tipo` em `lib/*.ts`, lembrar que a rota que recebe a resposta (`app/api/f/[token]/route.ts`, não compartilhada entre apps) precisa importar esse módulo (`import "@/lib/pdi"`, efeito colateral) para o callback já estar registrado quando a rota carrega.
- (US-052) `scripts/verificar-jargao.mjs` não filtra identificadores de código, só comentários/atributos técnicos/`fetch(...)`/`process.env.*` — a palavra proibida "token" não pode aparecer em `components/*.tsx` nem em `app/page.tsx` **de jeito nenhum**, nem como nome de variável/campo JSON (ex.: `resposta.token`), só como texto renderizado. Por isso a rota que gera o link de autoavaliação devolve `{ codigo: token }` (campo renomeado na resposta da API) em vez de `{ token }`, e o componente do diálogo só lida com `codigo` — o arquivo da rota em si (`app/api/.../route.ts`) não é varrido, então pode usar `token` livremente por dentro.
- (US-053) `lib/notificacoes.ts` (novo arquivo compartilhado, copie sem alterar): `enviar({ canal, destino, titulo, texto, link })` não recebe credenciais como parâmetro — lê `getConfig("NOTIFICACOES_...")` de `lib/store.ts` internamente, mesmo padrão de `lib/mcp.ts` lendo `MCP_CODIGO_ACESSO` direto. - **(US-070) Gotcha de fuso horário ao converter um `Date` para "AAAA-MM-DD" (relevante para qualquer `dataUnica` de `lib/rotinas.ts` ou qualquer data-only string nova):** nunca usar `date.toISOString().slice(0, 10)` para gerar a string — `toISOString()` converte para UTC, e num fuso negativo (ex.: Brasil, UTC-3) isso pode empurrar a data para o dia seguinte ou anterior dependendo da hora local no momento do cálculo. Montar a string a partir das partes locais (`getFullYear()`/`getMonth()+1`/`getDate()`, com `padStart(2,"0")`) evita o problema — é o que `lib/checkins.ts` faz (`paraDataLocal`). Do lado da exibição existe uma armadilha simétrica: `data()`/`lib/formato.ts` recebe uma string "AAAA-MM-DD" e o `new Date(string)` do JS interpreta datas sem hora como meia-noite **UTC**, então formatar essa string direto num fuso negativo mostra o dia anterior (mesmo bug pré-existente em `descreverAgenda`/`components/Rotinas.tsx` para rotinas "unica", não corrigido ali por estar fora do escopo desta história). Correção usada em `components/LembrarCheckins.tsx` (mesmo truque já usado por `prazoComData` em `app/page.tsx`): construir `new Date(`${aaaa-mm-dd}T00:00:00`)` (meia-noite local, sem "Z") e passar o objeto `Date` para `data()`, nunca a string crua.
- **(US-070) Padrão para uma rotina "unica" criada por um botão do resultado (não pelo formulário genérico "Nova rotina" de `/setup`):** registrar o executor em `registrarExecutor(tipo, fn)` (`lib/rotinas-do-app.ts`, via um arquivo próprio como `lib/checkins.ts`) **sem** adicionar o tipo em `TIPOS_ROTINA` — assim ele não aparece no seletor genérico (que não sabe coletar os parâmetros específicos, ex. "de qual PDI"), mas continua funcionando normalmente com `executarVencidas()`/"Executar agora" e aparecendo na tabela do cartão "Rotinas" (com o `tipo` cru como rótulo, já que `tipos.find(...)` não encontra correspondência — não quebra, só fica menos bonito). A criação de fato acontece chamando `criar()` de `lib/rotinas.ts` direto de uma rota própria do app (aqui, `app/api/pdi/checkins/route.ts`), sem passar por `POST /api/rotinas` (que validaria contra `TIPOS_ROTINA`).
- **(US-070) Anexar dados a um resultado depois de salvo, sem tocar no schema gerado pela IA:** o tipo do resultado (`PDI`) ganhou um campo opcional (`acompanhamento?: EntradaAcompanhamento[]`) que a IA nunca preenche — é só lido/escrito por código do app via `atualizarSaida(id, novaSaida)` (já existia em `lib/historico.ts`). Um `registrarCallback` de um segundo `tipo` de formulário (aqui `"checkin-pdi"`, ao lado de `"autoavaliacao"`) pode gerar efeito colateral num resultado de um `tipo` totalmente diferente (`"pdi"`) — os dois sistemas (`lib/formularios.ts` e `lib/historico.ts`) não têm nenhum acoplamento direto, então isso é seguro; o único requisito é que o arquivo que faz `registrarCallback` esteja importado (efeito colateral) tanto em `lib/rotinas-do-app.ts` (para o executor rodar) quanto em `app/api/f/[token]/route.ts` (para o callback estar registrado quando alguém responde ao formulário) — replicar as duas importações ao criar qualquer novo par executor+callback.
