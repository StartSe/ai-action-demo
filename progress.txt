## Codebase Patterns
- **(Ciclo "novos-apps", US-034) Segunda caixa/provedor para uma integração que já existia (ex.: Outlook ao lado do Gmail em `custos-ia`): parametrize a lib por um tipo `Provedor` definido em `lib/types.ts` (sem imports `node:*`, para `app/page.tsx` também usar) com uma tabela provedor → nomes de chaves, uma classe de erro mãe (`ErroEmail`) e subclasses por provedor (a rota mapeia só a mãe → 502), e um só componente de cartão com textos por provedor renderizado N vezes (`id={provedor}` mantém `/setup#<id>`).** A rota de estado (`/api/<recurso>/[provedor]`) devolve `oauthUrl`/`redirectUri`: um `"use client"` não pode conter o literal `/api/setup/...` fora de `href="..."`/`fetch(...)`, senão `verificar-jargao` acusa "/setup".
- **(Ciclo "novos-apps", US-034) Microsoft Graph, `/me/messages`: `$search` e `$filter` não podem ir juntos** — a data entra na KQL (`received>=AAAA-MM-DD`), o `$filter=receivedDateTime ge ...` fica como plano B para quando a busca é rejeitada com 400 (só a consulta padrão cai no plano B; consulta própria rejeitada é erro de quem a escreveu). Sempre `Prefer: IdType="ImmutableId"` (ids mudam ao mover de pasta e a dedup por referência falharia), `Prefer: outlook.body-content-type="text"` para não percorrer MIME, anexos listados com `$select` sem `contentBytes` e baixados um a um. O refresh token da Microsoft **rotaciona**: gravar o novo a cada renovação (e nunca defini-lo por variável de ambiente em produção). Query com `encodeURIComponent` (`%20`), não `URLSearchParams` (`+`).
- **(Ciclo "novos-apps", US-033) App novo criado a partir de uma cópia do `pdi-time` tem sete arquivos que precisam ser adaptados à mão e que nenhum verificador pega:** `app/setup/page.tsx` (marca/nome/área), `components/AcessoMCP.tsx` (a frase do que o assistente faz, os dois "o <app> aparece na lista/nas ferramentas" e, sobretudo, a chave de `mcpServers` na configuração pronta — sai `"pdi-time"` como nome do servidor no Claude Desktop), `app/r/[id]/not-found.tsx` e `app/imprimir/[id]/not-found.tsx` (a frase "Gere um novo <artefato>"), `app/layout.tsx`, `package.json` e `package-lock.json` (`"name"`). `scripts/verificar-padrao.sh` não acusa (esses arquivos são próprios de cada app por design) e `verificar-jargao.mjs` também não (o texto está em bom português — só fala do app errado). O que acha é abrir a captura de `/setup` do app com a ferramenta Read. Um app sem a capacidade `rotina` também não deve renderizar `<Rotinas />` em `app/setup/page.tsx` (fica um cartão morto "Nenhum tipo de rotina disponível neste app ainda").
- **(Ciclo "novos-apps", US-033) "Botão primário visível sem rolagem" se mede, não se olha:** a captura de página inteira sempre mostra o botão, mesmo quando ele está abaixo da dobra. Quando não couber, na ordem: encurtar o lead e as dicas redundantes (a dica que repete o placeholder é a primeira a sair), diminuir a altura mínima de um textarea (`min-h-28`/`min-h-32`; `min-h-44` é alto demais para um painel) e, só então, apertar o espaçamento do formulário com uma classe própria em `app/globals.css` (depois de `/* Específico deste app */`) — nunca editando `components/ui.tsx`, que é compartilhado e comparado entre os dezessete.
- **(Ciclo "novos-apps", US-033) Layout de força com grupos desconexos (um grupo por tema, por categoria etc.) precisa de repulsão com alcance limitado** (`dist > 1.5 * k` → ignora) **e de reenquadramento no fim** (bounding box → área com margem), nunca de grampo nas bordas durante a simulação: sem isso os grupos se afastam indefinidamente, todos os nós encostam no limite e o desenho vira um retângulo de pontos. - **(Ciclo "novos-apps", US-033) Erro de integração não conectada responde 400, não 502.** Quando o cliente de um serviço externo tem um erro único (`ErroX`) mapeado para 502, criar a subclasse `XNaoConectado extends ErroX` e tratá-la antes, com 400: configuração faltando é problema do pedido, não do provedor. Barra de barras com número variável de colunas sempre precisa de largura máxima (`w-1/2 max-w-14`): com uma coluna só, `w-1/2` desenha duas barras do tamanho do cartão.

Por isso `numero`/`data` moraram para `lib/formato.ts` (arquivo puro, sem `"use client"`), reexportados por `ui.tsx` para não quebrar quem já importa de lá; Server Components (como páginas de impressão/leitura) devem importar esses helpers direto de `@/lib/formato`. Ao replicar essa fundação para os outros 9 apps, copiar `lib/formato.ts` junto com `ui.tsx`.
- CSS Paged Media: para aplicar `size`/`margin` de impressão só numa página específica (não no documento inteiro), usar `@page nome { ... }` mais a propriedade `page: nome;` no container da página (ex.: `.print-sheet { page: folha-impressao; }`), em vez de um `@page` global sem nome — Chrome/headless respeitam isso (confirmado gerando PDF com `chromium --headless --print-to-pdf` e inspecionando com `pdfinfo`/`pdftoppm`). Dentro do `@media print`, `break-inside: avoid` em `.card`/`.summary` evita cortar um cartão ao meio entre páginas.

Mesmo princípio já usado em `lib/formato.ts` (US-012): nunca importar de um arquivo com `node:sqlite`/`node:fs` a partir de um "use client".
- `eslint-plugin-react-hooks@7` (via `eslint-config-next`) faz uma análise de estabilidade rasa para `react-hooks/exhaustive-deps`: uma função declarada no corpo do componente (ex.: `gerar`) que só chama setters de `useState`/`fetch` é tratada como estável e não precisa entrar no array de dependências de um `useEffect` que a referencia — mas se essa função chamar OUTRA função também declarada no corpo do componente (ex.: `gerar` chamando `carregarHistorico()`), a análise não desce mais um nível e passa a tratar `gerar` como instável, acusando "missing dependency" no efeito que a usa. Correção: evitar que uma função "estável" (chamada dentro de um efeito) chame outra função irmã do componente; inline a chamada (repetir o `fetch(...).then(setState)` em vez de extrair para uma função e chamá-la de dentro de `gerar`) resolve sem precisar de `useCallback` (não usado em nenhum lugar deste projeto).

- **(US-006 do prd.json)** Num container `flex flex-col md:flex-row` (lado a lado no desktop, empilhado no celular — padrão comum para "gráfico + painel lateral"), a classe `flex-1` (sem prefixo) no item que também tem uma altura explícita (`h-[Npx]`) e filhos só `position: absolute` (sem altura intrínseca) **zera a altura desse item no celular**: em `flex-col`, `flex-1` = `flex: 1 1 0%` no eixo vertical, e sem outro irmão competindo por espaço livre num pai de altura automática, o item encolhe para ~0 (a altura explícita é ignorada). Sintoma: `getBoundingClientRect().height` bem menor que o valor da classe `h-[...]`, e cliques em elementos filhos absolutamente posicionados dentro dele falham com "intercepts pointer events" do Playwright (o container, com altura ~0, "rouba" o clique). Correção: usar `w-full md:flex-1` (só cresce/encolhe no eixo horizontal do modo desktop) em vez de `flex-1` cru. Relevante para qualquer componente futuro com esse mesmo desenho responsivo.
- **(US-006 do prd.json)** Para um grafo de nós e arestas em SVG puro (sem biblioteca), a técnica que evita o problema já registrado de texto escalando junto com o `viewBox` (primeira entrada desta seção, sobre gráficos de barra) é: desenhar só as formas geométricas (linhas, círculos) dentro do `<svg>`, com `preserveAspectRatio="none"` para esticar exatamente como um `div` com `width/height: 100%` esticaria; os **rótulos** (`<span>`/`<button>` de texto) ficam fora do SVG, em HTML normal, posicionados por porcentagem (`left:`/`top:` = posição virtual dividida pelo tamanho virtual × 100%) sobre o mesmo container `position: relative`. Como a porcentagem escala exatamente igual ao `preserveAspectRatio="none"` do SVG, formas e rótulos ficam alinhados nas mesmas coordenadas, mas o texto (classe Tailwind `text-[Npx]`) nunca escala, porque não está dentro de nenhuma transformação do SVG. Também: um container com `overflow-hidden` corta rótulos HTML de nós próximos da borda (texto centralizado num nó perto da borda estoura a largura do container) — o SVG interno já tem `overflow:hidden` por padrão do user agent (as linhas continuam contidas ao viewBox), então é seguro remover o `overflow-hidden` do container para deixar só os rótulos (não as formas) vazarem visualmente quando precisarem.
