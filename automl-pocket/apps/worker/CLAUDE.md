# Worker Python (BullMQ)

- Estrutura: `main.py` é o entrypoint (asyncio + `bullmq.Worker` na fila "datasets"); a lógica dos jobs vive no pacote `jobs/` (`parsing.py`, `inference.py`, `dataset_parse.py`, `db.py`).
- Jobs síncronos (pandas/sqlite3) devem rodar via `asyncio.to_thread(...)` dentro do processor para não bloquear o event loop do BullMQ.
- Novos jobs: adicionar um branch por `job.name` no `process()` de `main.py`. O nome da fila e os `JOB_OPTIONS` devem espelhar `apps/web/src/lib/queue.ts`.
- Predição síncrona (US-042): o web enfileira `model:predict` na fila **"predictions"** com payload `{modelId, rows: [{col: valor}]}` e espera o **returnvalue** do job via `QueueEvents.waitUntilFinished` (helper `runPrediction` em `apps/web/src/lib/predictions.ts`, timeout 30s). A lógica vive em `jobs/model_predict.py`: artefato joblib com cache LRU em memória por modelId (retreino gera model id novo → cache nunca fica stale); colunas faltantes viram nulos (o frame é montado só com as `feature_columns`), desconhecidas são ignoradas. Retorno: classificação `[{prediction, probability, probabilities: {classe: p}}]`, regressão `[{prediction}]`. Erros esperados = `PredictionError` (pt); `run_predict_job` embrulha exceções inesperadas na mensagem genérica — o failedReason que chega ao web está sempre em português.
- Predição em lote (US-045): job `model:predict-batch` na mesma fila "predictions", payload `{modelId, inputPath, outputPath}` (caminhos relativos ao UPLOAD_DIR, subdir `batches/`; `_resolve_batch_path` rejeita path traversal). A lógica vive em `jobs/model_predict_batch.py`: lê CSV/XLSX/XLS com `read_dataset_file`, limite de 5.000 linhas (`MAX_BATCH_ROWS`; o texto do lote no web cita o valor — sincronizar), exige ≥1 coluna do modelo no arquivo (colunas ausentes viram nulos via `reindex`); saída é CSV utf-8-sig com as colunas originais + `predicao` (+ `probabilidade` na classificação). O web (rota `/app/[slug]/batch`) grava a entrada, espera via `runBatchPrediction` (timeout 120s) e remove entrada+saída no finally. **Gotcha:** o failedReason do bullmq Python chega JSON-serializado (`"mensagem"` com escapes `\uXXXX`) — o web decodifica em `decodeFailedReason` (src/lib/predictions.ts).
- **Bug conhecido do parser** (`parsing.py`): em CSV de UMA coluna, o sniffer (`sep=None`) pode deduzir um delimitador errado em vez de falhar (ex.: header `idade` → colunas `i,a,e` com sep="d") — o fallback de coluna única nunca roda. Afeta dataset:parse e o lote da US-045.
- Concorrência da fila "training" (US-001 beta; default baixado para 2 no Pocket US-016 — 1 único container web+worker no Render, sem a VM dedicada de 8 vCPUs da prática antiga): `training_concurrency()` em main.py lê a env `TRAINING_CONCURRENCY` (default 2) e passa como opção `concurrency` ao `bullmq.Worker`; a env vem do `.env` único que o compose repassa aos dois serviços. As filas "datasets" e "predictions" seguem com concorrência 1 (default).
- Revisão de layout (US-023): `db.layout_review_enabled()` (jobs/db.py) lê `LAYOUT_REVIEW_ENABLED` (default False; aceita true/1/yes/on, mesma regra de `apps/web/src/lib/layout-review.ts`); main.py loga o estado no start. Colunas `datasets.layout_diagnosis` (saída de `diagnose_layout`) e `datasets.parse_options` (`{sheets, combine, headerRow, transpose}`) e o valor `needs_review` do enum `dataset_status` existem desde a migration 0022. Tipos TS espelhados em `apps/web/src/db/schema.ts` (`LayoutDiagnosis`, `DatasetParseOptions`).
- dataset:parse com revisão de layout (US-024): `run_parse_job` devolve `PARSED` | `NEEDS_REVIEW` | `SKIPPED` e o main.py SÓ enfileira dataset:profile em `PARSED` (parado em needs_review, ninguém enfileira nada — a rota `/api/datasets/[id]/layout` do web grava `parse_options`, volta o status a "parsing" e reenfileira o dataset:parse). Ordem em `_parse_and_persist`: `diagnose_layout` → UPDATE `layout_diagnosis` + **commit imediato** (o diagnóstico sobrevive ao rollback de um parse que falhe depois, para a tela de revisão) → `should_pause_for_review` (flag ligada E `needsReview` E `parse_options IS NULL` E `NOT is_example`) → UPDATE status='needs_review' ou `read_dataset_file(source, format, parse_options)`. `parse_options` é aplicado sempre que não for NULL, com a flag ligada ou não. Datasets `is_example` nunca param (não há usuário para revisar o seed; `Sales_Example.xlsx` tem 2 abas com dados). `FakeConn` de `tests/test_dataset_parse.py` tem `find(fragment)`, contagem de commits/rollbacks e `row` para o SELECT — reaproveitar em vez de criar outro fake.
- Opções de layout em `read_dataset_file(path, format, options)` (US-024): `sheets` (nomes; inexistente/vazia → ParseError "A aba 'X' não existe…"; sem `combine` só a PRIMEIRA escolhida é lida), `headerRow` (índice físico 0-based: `header=` no read_excel, `skiprows=` no read_csv — ambos contam linhas em branco, igual ao diagnóstico), `transpose` (lê com `header=None` + skiprows e vira a grade em `_transpose`: 1ª coluna vira cabeçalho, duplicados ganham `_2`, `_3`, célula vazia vira "Unnamed: N"; o top-left vazio vira a coluna "Unnamed: 0" com os rótulos antigos) e `combine` (concatena as abas escolhidas exigindo `column_fingerprint` igual — nomes normalizados por `normalize_column_name`, a MESMA função do `schemaFingerprint` do diagnóstico, por isso `layout.py` importa dela; colunas das demais abas são renomeadas para os nomes da 1ª e a coluna `ORIGIN_COLUMN`="aba_origem" recebe o nome da aba; fingerprints diferentes → ParseError "As abas X e Y têm colunas diferentes e não podem ser combinadas."). csv ignora `sheets`; json ignora tudo. O pós-processamento (dropna/Unnamed/título) roda igual depois das opções; `options=None` e as opções default produzem frames idênticos (teste de regressão trava isso).
- Paralelismo interno de cada treino (US-002 beta): `MODEL_N_JOBS` em jobs/automl.py (env `MODEL_N_JOBS`, default 2) é o `n_jobs` de Random Forest e XGBoost — nunca voltar a `n_jobs=-1` (4 treinos simultâneos disputariam os 8 vCPUs); MLP não tem n_jobs, é coberto por `OMP_NUM_THREADS=2` no `.env` (threads BLAS/OpenMP).
- Substituição de modelos no retreino (US-004 beta): ao persistir um treino, `_replace_project_models` em model_train.py re-aponta os `deployments` do projeto para o modelo novo e SÓ DEPOIS deleta os modelos antigos do projeto (deployments.model_id tem ON DELETE CASCADE — inverter a ordem apagaria o deployment publicado com slug/chave a cada retreino); os artefatos .joblib órfãos são removidos best-effort (`unlink(missing_ok=True)`) APÓS o commit, e o DELETE por training_job_id (retry) continua vindo antes do INSERT para o artefato recém-gravado nunca entrar na lista de remoção. Cada projeto tem no máximo 1 linha em models após um treino.
- Rastreio de bytes (US-007 beta): o worker mantém `datasets.size_bytes` e `models.size_bytes` (bigint nullable; null conta como 0 na quota da US-008). dataset:parse grava SET absoluto = arquivo original + parquet gerado (idempotente no retry); dataset:transform INCREMENTA com `COALESCE(size_bytes, 0) + tamanho do parquet da versão` em `_persist_version`; model:train grava o tamanho do .joblib comprimido no INSERT de models. Ao mexer nesses SQLs, manter os três pontos em sincronia — a quota de armazenamento do web soma essas colunas.
- Eventos duráveis de treino (US-002 de métricas duráveis): model_train.py grava `training.succeeded`/`training.failed` em audit_logs na MESMA transação do UPDATE de status do training_job (`_log_training_event` NÃO commita — participa da transação do chamador; nunca chamar fora de uma). user_id fica fora do INSERT (NULL — a atribuição vem do join com o `training.start` do web pelo resource_id); retry gera evento novo de propósito. Metadata de sucesso: identificadores + `durationSeconds` (RETURNING de EPOCH(updated_at−created_at) no próprio UPDATE de status) + `primaryMetric {name, value}` + `metrics` (shape de models.metrics). **Gotcha**: no multiclasse `selectionMetric` é "f1_macro" mas os candidatos reportam a chave "f1" — `_primary_metric` faz o fallback. Falha: `errorMessage` truncada em `ERROR_MESSAGE_LIMIT` (500). Nunca colocar valores das linhas do dataset na metadata; os relatórios que leem `audit_logs` dependem desses shapes.
- Treinamento: o web enfileira `model:train` na fila **"training"** (separada de "datasets") com payload `{ trainingJobId }`; `main.py` roda um segundo `bullmq.Worker("training", ...)`. O `training_jobs.config` tem `{target, ignoredColumns, mode: "fastest"|"high_quality"|"higher_quality"|"production" (orçamento de configs 1/2/4/8 em MODE_CONFIG_COUNTS; aliases legados fast/standard/full aceitos via mode_config_count — jobs antigos e retries), timeColumn, forecastHorizon: int|null (só forecasting; null = automático), aggregation: "auto"|"hourly"|"daily"|"weekly"|"monthly"|"quarterly" (só forecasting; "auto" = frequência inferida), forecastModel: "auto"|"naive"|"holt_winters"|"arima" (só forecasting; "auto" = escolha pelo backtest), idColumn: string|null (só forecasting; null/"" = série única), problemType: "classification"|"regression"|"forecasting"}` — já validado pelo web (alvo é category/number; timeColumn, forecastHorizon, aggregation e forecastModel só em forecasting; o horizonte já vem inteiro entre 1 e 365 e a agregação sempre num dos seis valores).
- AutoML (`jobs/automl.py`): `train_classification` e `train_regression` são funções puras com a MESMA assinatura (df, target, ignored_columns, mode, column_types, on_progress) → `TrainingResult`; o loop de candidatos é compartilhado em `_run_candidates` (métrica primária + `higher_is_better`). O dispatch por `problemType` vive no dict `TRAINERS` de model_train.py; os kwargs extras do forecasting saem de `_forecasting_kwargs(config)` (camelCase → snake_case: timeColumn, forecastHorizon, aggregation, forecastModel, idColumn — ausente/nulo = automático ou série única), função pura para testar o repasse sem banco.
- Forecasting (`jobs/forecasting.py`): `train_forecasting` agrega a série pela frequência inferida do espaçamento mediano (h/D/W/MS/QS/YS + período sazonal), interpola lacunas e faz split temporal (últimas ~20% observações = janela de backtest). Candidatos: naive (último valor), Holt-Winters (statsmodels) e ARIMA (grade SARIMAX; sazonal só com 2 ciclos completos e m ≤ 24); seleção por MAPE (fração, não %; zeros ignorados no denominador). O kwarg `aggregation` (US-010) força o bucket temporal em vez de inferi-lo: "auto" mantém `_infer_frequency`, os demais valores viram o alias pandas de `_AGGREGATION_ALIASES` (hourly→h, daily→D, weekly→W, monthly→MS, quarterly→QS) e herdam período sazonal/rótulos da entrada correspondente de `_FREQUENCIES` — a agregação continua sendo a **média** por bucket, e `insights.forecast.frequency/frequencyLabel` refletem a escolha. Agregação manual passa por `_check_manual_aggregation` (antes da interpolação): menos de `MIN_POINTS` buckets ou menos de `MIN_OBSERVED_FRACTION` (50%) deles com observação real viram `TrainingError` em pt (grossa demais / fina demais) — sem isso o `.interpolate()` inventaria a série inteira. O kwarg `forecast_horizon` (US-009) só dimensiona a previsão futura: `_resolve_horizon` devolve (horizonte, "manual"|"auto") — automático = 30% do comprimento da série, sempre preso a [`MIN_HORIZON`, `MAX_HORIZON`] = [1, 365]. A janela de backtest continua `min(20% da série, `MAX_BACKTEST_SIZE`=90)`, então mudar o horizonte NÃO altera treino, métricas nem escolha do vencedor. O kwarg `forecast_model` (US-011) fixa o algoritmo: `_select_candidates` filtra a tupla de `_forecast_candidates` pela chave escolhida ("auto"/None/chave desconhecida mantêm os três — o worker nunca fica sem candidato por causa da entrada), então `models.metrics.candidates` e o `on_candidates` da tela de progresso passam a ter UM item só; a grade de configs do algoritmo continua limitada por `mode_config_count`, e se nenhuma delas convergir o erro é específico ("O modelo {rótulo} não conseguiu se ajustar a esta série. Tente Melhor backtest para escolha automática."). O "pipeline" do TrainingResult/artefato é um `ForecastModel` picklável com `.forecast(h)` → DataFrame value/lower/upper (IC 95%: conf_int do SARIMAX; resid_std×√h nos demais). Configs que não convergem são puladas (`configsTested` conta só as que rodaram).
- Multi-série / ID Field (`_build_series_by_id`, US-013): quebra o DataFrame em uma `SeriesEntry` (id, label, series já agregada, points) por identificador e devolve `(entries, descartadas, total_encontrado)`. A frequência é resolvida UMA vez por `_resolve_frequency` sobre os timestamps **distintos** de todos os pontos (usar o índice bruto inferiria "horária": 25 lojas no mesmo dia dão espaçamento zero) e é reaplicada a cada série, para que os períodos sejam comparáveis. Cada série passa pela mesma normalização de `_build_series` (coerção, média dos timestamps duplicados, `resample().mean().interpolate(method="time").ffill().bfill()`). Descarte (contado em `descartadas`): menos de `MIN_SERIES_POINTS`=10 observações **reais** OU menos de 10 períodos depois da agregação — o corte pelas observações reais é o que impede 3 pontos espalhados por um ano de virarem 365 períodos interpolados. As entries voltam ordenadas por `points` desc (desempate por label) e cortadas em `MAX_SERIES`=25; as que caem fora do teto NÃO entram em `descartadas`, então `total - descartadas - len(entries)` é o truncamento. Identificador nulo/vazio vira o grupo `id=""` com `label` = `UNIDENTIFIED_SERIES_LABEL` ("(sem identificador)"); `_series_key` normaliza o resto (3.0 → "3"). Nada sobrando → `TrainingError` em pt. `_check_manual_aggregation` NÃO roda por série (uma subsequência ruim não pode derrubar o treino inteiro — o corte de 10 períodos é quem filtra).
- Artefato multi-série (`MultiSeriesForecastModel`, US-014): wrapper picklável que guarda `{series_id: ForecastModel}` (a ordem de inserção do dict é a ordem das séries, e vira `series_ids`) e expõe `forecast(horizon, series_id)` → o mesmo DataFrame value/lower/upper do `ForecastModel` daquela série. `series_id` desconhecido levanta `KeyError` em pt listando as séries disponíveis; construir sem nenhuma série levanta `ValueError`. É esse objeto que vai como "pipeline" do artefato quando há ID Field (a série única continua com o `ForecastModel` puro) — o `joblib.dump(..., compress=ARTIFACT_COMPRESS)` do model_train.py serializa os N modelos statsmodels juntos, então o .joblib cresce ~linearmente com o nº de séries e `models.size_bytes` (quota de armazenamento) acompanha.
- Treino multi-série (`_train_multi_series`, US-015): `train_forecasting` ganhou o kwarg `id_column`; preenchido, ele desvia para esse caminho logo depois do `notify(5, ...)` — a série única segue byte a byte o código de antes (o AC pede resultado idêntico, então NÃO unificar os dois loops de candidatos). A escolha de algoritmo é **global**: cada configuração é pontuada por `_score_config` sobre a amostra das `SELECTION_SAMPLE_SIZE`=10 séries mais longas (as entries já vêm ordenadas), somando mape/rmse/mae **ponderados pelo nº de pontos de teste** de cada série; série em que a config não converge é pulada (não entra na ponderação) e config sem nenhuma série pontuável é descartada. O vencedor é refitado na série COMPLETA de TODAS as entries (não só na amostra) por `_fit_series_model`, que **cai no baseline naive** se os params vencedores não convergirem naquela série — a alternativa seria perder a série inteira por causa de uma escolha feita sobre a amostra. O split por subsequência é `_split_series` (dataclass `_SeriesSplit` com train/test/scale): mesma fração de 20%, mas com pisos próprios (`MIN_SERIES_TRAIN_POINTS`=6, `MIN_SERIES_TEST_POINTS`=2) porque uma subsequência tem só 10 períodos e não caberia no `MIN_TRAIN_POINTS`=12 da série única. `models.metrics` mantém o shape exato (candidatos com as métricas agregadas da amostra; `rows` soma todas as séries), `on_candidates` continua com um item por algoritmo (a tela de progresso não muda) e `on_progress` reporta duas fases: seleção `SELECTION_PROGRESS_START`(5)→`SELECTION_PROGRESS_END`(60) e refit 60→`REFIT_PROGRESS_END`(92) com o rótulo da série na mensagem. O período sazonal sai de `_resolve_frequency` sobre a UNIÃO dos períodos das séries. `TrainingResult.insights` volta `None` no caminho multi — os insights multi-série são a US-016 (e `model_train.py` ainda não repassa `config.idColumn`, também US-016). Custo medido (25 séries × 180 pontos, 4.500 linhas): 9,3s em `fastest`, 9,6s em `high_quality`, 15,2s em `production` — ~12x uma série única de 180 pontos (0,8s), porque a seleção roda em 10 séries e o refit em 25.
- Insights multi-série (`_multi_series_insights`, US-016): com ID Field as chaves de topo de `insights.forecast` descrevem a **série agregada** (`_aggregate_series` = soma das subsequências por período, regularizada por `resample(freq).sum(min_count=1)` + interpolação — período em que só parte das séries reportou soma só essas) e ganham `idColumn`, `excludedSeries` (nº de séries curtas descartadas), `truncatedSeries: {shown, total}` (**só quando** o teto de `MAX_SERIES` cortou alguma; `total` = nº de identificadores encontrados no dataset, então shown + truncadas + excludedSeries = total) e `series: [{id, label, points, mape, history, predictions, backtest?, seasonality}]`. A agregada é tratada como uma série de verdade: `_split_series` + `_backtest_series` (refit do vencedor no treino dela) e `_fit_series_model` na série completa para a previsão futura — por isso o `mape` de topo é o erro da **previsão agregada**, e NÃO a média ponderada da amostra de seleção, que continua em `models.metrics` (com fallback para ela se o refit da agregada falhar). O horizonte automático (30%) sai do comprimento da agregada e vale para todas as séries. Caps de histórico: `HISTORY_LIMIT`=365 na agregada (visão default do relatório) e `MULTI_HISTORY_LIMIT`=120 por subsequência. O backtest por série refita o vencedor só na janela de treino e **cai no naive** se os params não convergirem ali (espelha o fallback de `_fit_series_model`, para o MAPE da linha bater com o modelo que de fato prevê aquela série); `mape` da série é `None` se nem o naive convergir. `feature_columns` do artefato vira `[time_column, id_column]`. Tamanho medido do JSONB (25 séries): 375 KB com 180 pontos/série (horizonte auto 54), 888 KB com 730 pontos/série, ~1,08 MB no pior caso (horizonte manual 365 × 25 séries) — quem manda no tamanho é `predictions`, não o histórico. Blocos de insights compartilhados entre os dois caminhos: `_summary_payload`, `_seasonality_payload`, `_history_points`, `_prediction_points` (mudar um muda a série única E a multi).
- `TrainingResult.insights` é persistido em `models.insights`, com uma chave por tipo de problema. Forecasting: `{forecast: {frequency, frequencyLabel, seasonalPeriod, horizon, horizonSource: "auto"|"manual", horizons (derivado de `_horizon_options`: os valores de [7,30,90] menores que o horizonte, mais o próprio horizonte — nunca vazio, nunca acima do horizonte), mape, summary{mape,text}, seasonality{detected,period,strength,label,text,buckets}, history: [{date,value}] (cap 365), predictions: [{date,value,lower,upper}] (exatamente `horizon`períodos), backtest?{points:[{date,actual,predicted}] (cap`BACKTEST_POINTS_LIMIT`=180, últimos registros), rmse, mae, mape, trainPoints, testPoints}}}` — a UI da US-024 fatia `predictions` pelos horizontes, sem novo treino. O `backtest` vem de `_backtest_series` (refit do vencedor SÓ no treino, mesmos params do loop de candidatos) — por isso rmse/mae/mape são idênticos aos do candidato vencedor em `models.metrics`; esse refit extra não toca o artefato nem a previsão futura, e a chave é OMITIDA se o refit falhar (relatórios antigos também não a têm → tratar como opcional no web). A sazonalidade é detectada pela autocorrelação da série diferenciada no lag sazonal (`_detect_seasonality`, limiar 0.2) — independe do algoritmo vencedor; `label` é o rótulo do ciclo em pt (ex.: D→"semanal", MS→"anual") e vem da 5ª posição de `_FREQUENCIES`. `seasonality.buckets` (US-002) vem de `_seasonal_buckets(series, freq)`: índice sazonal clássico (razão entre o valor e a média móvel **centrada** de um ciclo completo — `_centered_moving_average` usa a 2×MA de pesos 0,5 nas pontas quando a janela é par), com o impacto de cada bucket = média das razões do bucket como desvio da média geral (`0.145` = +14,5%). Quais buckets existem por frequência e quantos períodos formam um ciclo deles está em `_SEASONAL_BUCKETS` (h→hora/dia da semana/mês, D→dia da semana/mês/trimestre, W e MS→mês/trimestre, QS→trimestre, YS→nenhum); um bucket só entra com ≥2 ciclos completos na série e denominador ≥ `MIN_SEASONAL_DENOMINATOR` — por isso a lista costuma vir com MENOS buckets que o máximo teórico (série diária de 1 ano não tem mês nem trimestre). A lista pode ser vazia e os relatórios antigos não têm a chave.
- Classificação (`jobs/insights.py`, US-017): `compute_classification_insights` é função pura chamada dentro de `train_classification` com o pipeline vencedor AINDA ajustado só no treino (antes do refit final) — as probabilidades/métricas do report batem com as de `models.metrics`. Shape de `models.insights.classification`: `{positiveClass, methodology, summary{accuracy,correct,total,baselineAccuracy,vsBaseline,text}, confusionMatrix{positiveClass, cells[{kind: tp|fp|tn|fn, label, count, of, pct, text}]} (pct condicional à classe REAL: tp/fn sobre `of`=positivos reais — tp é o recall —, fp/tn sobre `of`=negativos reais; relatórios antigos não têm `of`e o pct era sobre o total), perClass[{className,accuracy,precision,recall,f1,count}], topFields[{column,importance,pct}] (permutation importance na validação, pct normalizado p/ somar 100), topFactors[{column,overallRate,factors[{label,count,pct,outcomeRate,impact,text}]}] (2 campos líderes; numéricas/datas em ~4 faixas por quantil, categóricas por valor), segments[{level: high|medium|low, label, size, sizePct, outcomeRate, overallRate, vsOverall, avgProbability, attributes[{column,kind,…,text}], text}] (KMeans 1-D sobre a probabilidade prevista em todas as linhas), thresholdChart{positiveClass, bins[{from,to,positive,negative}] (20 bins)}, sampleRows{columns, rows[{values,actual,predicted,probability}] (≤100, prob desc)}}. A classe "positiva" do report é sempre a minoritária (na binária = positive_class da seleção). Todos os textos em pt;`impact`/`vsOverall` em pontos percentuais.
- Regressão: candidatos baseline (média)/linear_regression/random_forest/xgboost/mlp, seleção por RMSE (menor é melhor) na validação 80/20 sem estratificação; alvo convertido com `pd.to_numeric(errors="coerce")` e linhas não numéricas descartadas; `classes=[]` e `positive_class=None` no resultado; métricas por candidato: rmse, mae, r2 (r2 não-finito vira 0.0 p/ manter o JSON válido).
- Regressão (`jobs/insights.py`, US-018): `compute_regression_insights` é função pura chamada dentro de `train_regression` com o pipeline vencedor ajustado só no treino (antes do refit) — rmse/mae do summary batem exatamente com os do candidato vencedor em `models.metrics`. Shape de `models.insights.regression`: `{methodology, summary{medianErrorPct (±X%, mediana de |erro|/|real| com zeros fora do denominador; null se o alvo de validação for todo zero), rmse, mae, r2, text}, targetDistribution{mean, median, bins[{from,to,count,pct}] (10 bins sobre TODAS as linhas), text}, scatter{total, points[{actual,predicted}] (≤500, amostrados com seed fixa)}, topFields (mesmo shape/permutation importance da classificação; scorer default = R²)}`. A UI da US-023 consome esse shape.

"Ilegível" ≠ "vazia": `dataset_columns.stats.invalidCount` (gravado pelo dataset:parse = não vazios que falharam a conversão; preservado pelo dataset:profile e carregado adiante pelo dataset:transform; ausente = 0) — ilegível usa fração de nulos do parquet (vazios+ilegíveis) ≥99% filtrada por tipo, vazia desconta os ilegíveis. - **SQLite (Pocket US-015, substitui psycopg/Postgres)**: `jobs/db.py::connect()` abre `sqlite3.connect(SQLITE_PATH, timeout=5, isolation_level=None)` (autocommit — sem BEGIN implícito) com `PRAGMA journal_mode=WAL`/`busy_timeout=5000`/`foreign_keys=ON` e `row_factory=sqlite3.Row`; devolve um `contextlib.closing(conn)` (sqlite3.Connection não fecha sozinho no `with`, só comita/rollback). `SQLITE_PATH` (default `./data/pocket.db`) é o MESMO arquivo que `apps/web/src/db/index.ts` abre via `@libsql/client` (WAL permite os dois processos lerem/escreverem sem coordenação externa). Placeholders são `?` (não `%s`), sem cast (`::uuid`/`::column_type` saíram — SQLite não tipa colunas). `now()` → `db.now_ms()` (epoch ms UTC, mesmo formato do `integer(col, {mode:"timestamp_ms"})` do Drizzle). **Nenhuma tabela tem DEFAULT de PK ou timestamp no schema SQLite** (conferir `apps/web/drizzle/0000_pocket.sql` — só `NOT NULL`, sem `DEFAULT`): todo INSERT cru precisa incluir `id` (`db.new_id()`) e `created_at`/`updated_at` (`db.now_ms()`) explicitamente, mesmo que um INSERT antigo não os citasse. `RETURNING` e `executemany` continuam funcionando (SQLite ≥ 3.35, Python 3.12 já traz uma versão nova o bastante) — só troque `with conn.cursor() as cursor: cursor.executemany(...)` por `conn.executemany(...)` direto (`sqlite3.Cursor` não é context manager). Colunas JSON (`mode: "json"` do Drizzle) são TEXT puro: serializar com `db.json_dump(value)` e desserializar com `db.json_load(value)` ao ler qualquer coluna JSON de volta (`stats`, `config`, `metadata`, `metrics`, `insights`, `layout_diagnosis`, `parse_options`, `candidates`, …). Merge raso de dois objetos JSON é `json_patch(col, ?)` (usado em `dataset_profile.py` para os `layout_diagnosis.warnings`). Blocos que precisam ser atômicos (DELETE+INSERT+UPDATE de um parse/transform) abrem `db.begin_immediate(conn)` antes do primeiro write — sem isso, autocommit faria cada statement virar sua própria transação. Gravações de progresso de treino (`_set_progress`/`_set_candidates` em `model_train.py`) passam por `db.retry_on_locked(...)` (3 tentativas com backoff) porque competem com o web pelo mesmo arquivo com frequência alta — o `busy_timeout` do SQLite já cobre a maioria, isso é a segunda camada.
