## Notas específicas deste app

- `lib/historico.ts`/`lib/sensivel.ts`/`lib/formato.ts`/`instrumentation.ts`/`components/setup.tsx`/`lib/setup-comum.ts` são cópias literais de `pdi-time` (arquivos genéricos, sem lógica específica do app). Só `app/r/[id]/page.tsx`, `app/imprimir/[id]/page.tsx` e os `not-found.tsx` são próprios daqui, porque dependem do `Resultado`/tipo de dado deste app. A integração própria (Trello) mora só em `lib/integracoes.ts`.
- Este app não tem um "resultado" único como o PDI (um formulário que gera um plano). O "resultado" salvo no histórico é cada chamada ao agente (`POST /api/agente`): `entrada = { mensagem }`, `saida = ResultadoAgente` (resposta, ações, quadro, alterados). `GET /api/quadro` (carga inicial da página) devolve `meta` mas não salva no histórico — só ações do agente viram um link permanente.
- `Empty` é usado de verdade aqui (diferente de `Destaque`/`Dropzone` em `pdi-time`, que ficam só exportados): quando o quadro carregado tem zero cartões em todas as listas, `Stage` mostra `Empty` com a ilustração "quadro de três colunas" e o botão "Testar com um exemplo" chama `enviarMensagem(EXEMPLO_COMPOSTO)` diretamente.
- **Bug de corrida corrigido aqui, relevante para as próximas réplicas (US-018 a US-025):** o efeito que carrega o estado inicial (`carregarQuadro`/equivalente) e o efeito do atalho `?exemplo=1` disparam os dois com `setTimeout(..., 0)` no mesmo mount. Se ambos chamam a mesma API (ou uma API e a outra escrevem no mesmo estado), o que responder por último vence e pode sobrescrever `meta`/`id`/resposta do outro com dados mais "pobres" (sem citar a ação que acabou de rodar). Correção: o efeito de carga inicial verifica `?exemplo=1` e não dispara quando o atalho já vai carregar o estado sozinho via `enviarMensagem`/`gerar`.
- Também corrigido em `pdi-time/components/ui.tsx` (fonte compartilhada, então já replicado aqui): `Entregar` calculava `link` com `location.origin` direto no corpo da função, o que quebra com `ReferenceError: location is not defined` em `/r/[id]` e `/imprimir/[id]` (Server Components que renderizam esse Client Component no servidor). Corrigido com `typeof window !== "undefined" ? ... : undefined`. Ao replicar `ui.tsx` para os próximos apps, usar a versão já corrigida (não a versão antiga que só existia em capturas de tela anteriores a esta história).
- **Quadro de exemplo por visitante (US-034):** `lib/quadro-demo.ts` não guarda mais um único quadro em memória compartilhado por todo mundo; `quadroDemoPara(visitanteId)` devolve um `ProvedorQuadro` cujas funções fecham sobre `visitanteId` e leem/escrevem um `Map<string, EstadoVisitante>` no módulo (`estadoDe`/`quadrosPorVisitante`). O `visitanteId` vem de `lib/visitante.ts` (`visitanteId()`, cookie `visitante_id` httpOnly de 30 dias, criado via `cookies()` de `next/headers` — só funciona em Route Handlers, nunca em Server Components). As duas rotas que usam o quadro demo (`GET /api/quadro`, `POST /api/agente`) chamam `await visitanteId()` e passam para `quadroDemoPara`; `lib/trello.ts` (quadro real, genuinamente compartilhado) não precisa disso. `reiniciarQuadroDemo(visitanteId)` só dá `Map.delete`; a próxima leitura recria os 7 cartões iniciais (função `estadoInicial()`/`cartoesIniciais()`, com `randomUUID()` novo a cada recriação). Nova rota `POST /api/quadro/reiniciar` para o botão "Reiniciar quadro de exemplo" do painel (só aparece quando a resposta de `/api/quadro`/`/api/agente` traz `quadroDemo: true`, campo novo ao lado de `meta`/`id` nessas duas respostas — não confundir com `meta.demo`, que é sobre a IA, não sobre qual provedor de quadro está em uso).
- **`ProvedorQuadro` ganhou `atribuir({ cartaoId, responsavel })` (US-034):** antes não existia nenhuma forma de definir o responsável de um cartão já criado (só a criação aceitava, e sempre vazio). Implementado nos dois provedores: `lib/quadro-demo.ts` só seta o campo; `lib/trello.ts` resolve o nome digitado para um `idMembers` do quadro real (`encontrarMembroId`, mesma techa de correspondência aproximada — igual/contém — já usada em `mapaMembros`) e faz `PUT /cards/{id}` com `idMembers`. `lib/agente.ts` ganhou o tool `atribuir_cartao` (modo IA) e o gatilho por palavra-chave "atribua/atribuir/designe/designar/responsabilize" (modo sem IA, bloco dedicado em `processarSemIA`). Na tela, um cartão sem `responsavel` (`components/Quadro.tsx`) mostra o botão "Atribuir a alguém" (só quando `onAtribuir` é passado — ausente em `/r/[id]`/`/imprimir/[id]`, mesmo padrão de prop opcional já usado para a coluna de ação de `prospeccao-ia`) que só preenche o campo de comando (`Atribua o cartão "<nome>" a `) — não atribui sozinho, o usuário completa o nome e envia.
- **Confirmar antes de agir e Desfazer (US-035):** `lib/agente.ts` ganhou um segundo modo em `processarMensagem`/`processarComIA`/`processarSemIA`: `planejar: true` percorre a mesma lógica (tool calling ou palavras-chave) mas nunca chama os métodos mutantes de `ProvedorQuadro` — só lê (`listarListas`/`listarCartoes`/`obterQuadro`) para descrever o que faria, e devolve `{ plano: Acao[] }` em vez de `ResultadoAgente` (usei overloads de `processarMensagem` para o TypeScript escolher o tipo de retorno certo pela literal `planejar: true`/`false`/ausente, sem precisar de type guard em quem chama). A rota `POST /api/agente` só entra nesse modo quando `trelloConfigurado()` é verdadeiro (Trello real) **e** o corpo não trouxe `confirmar: true`; devolve `{ plano }` (sem `quadro`/`resposta`) quando há algo a confirmar, ou segue direto para a execução real quando o plano vier vazio (mensagem só de leitura, ex.: "como está o quadro?"). Em modo demo (quadro de exemplo, sem Trello) continua executando direto, sem plano, como antes de US-035.
  - `Rastro` (interno a `lib/agente.ts`) ganhou o campo `desfazer: Desfazer | null`, sobrescrito a cada ação mutante real (não durante `planejar`): as 3 ações reversíveis (`criar_cartao`→arquivar o criado, `mover_cartao`→voltar para a lista de origem, `comentar_cartao`→apagar o comentário) gravam os dados necessários; `atribuir_cartao`/`arquivar_cartao` zeram explicitamente para `null` (não são reversíveis nesta versão) — importante: é preciso zerar explicitamente nas ações não reversíveis, senão o `desfazer` de uma ação anterior fica "pendurado" e o botão ofereceria desfazer a ação errada quando a mensagem tem mais de um bloco (ex.: "crie X e atribua Y").
  - `ProvedorQuadro` (`lib/quadro.ts`) ganhou `removerComentario({ cartaoId, comentarioId })` e `comentar` passou a devolver `{ ok: true, comentarioId }` (antes só `{ ok: true }`) — implementado em `lib/quadro-demo.ts` (cada comentário em memória ganhou um `id` próprio via `randomUUID()`) e em `lib/trello.ts` (a resposta de `POST /cards/{id}/actions/comments` já é a Action criada, com `id`; desfazer usa `DELETE /actions/{id}/comments`, o mesmo endpoint documentado para apagar comentário, não o de apagar uma action genérica).
  - Nova rota `app/api/agente/desfazer/route.ts` (`POST { desfazer }`): re-resolve o provedor (Trello real ou quadro demo do visitante) e aplica a reversão certa por `desfazer.tipo`; devolve `{ ok, quadro }` atualizado. Não salva nada no histórico (desfazer não é uma nova entrada de "Últimos resultados").
  - No cliente (`app/page.tsx`), a resposta do agente pode trazer `plano` (nada foi executado ainda) OU `quadro`/`resposta`/`desfazer` (já executou): a UI guarda isso em dois estados independentes — `planoPendente` (mensagem + historico da conversa no momento do envio + os itens do plano, para reenviar exatamente a mesma mensagem com `confirmar: true` ao clicar "Confirmar") e `desfazerPendente` (o objeto `Desfazer` cru devolvido pelo servidor, com um `setTimeout` de 30 s que limpa o estado — guardado em `useRef` para poder cancelar/trocar o timer quando uma nova ação subsequente já tem seu próprio `desfazer`). Testado (sem Trello real disponível neste ambiente) forçando temporariamente `trelloConectado = true` na rota + Playwright (`playwright-core` via `npx`, apontando `executablePath` para o `chromium` do Homebrew) para clicar em Confirmar/Cancelar/Desfazer de verdade; a mudança de teste foi revertida antes do commit.

- **(US-072) Como uma ferramenta remota "genérica" chamada por este provedor normalmente só aceita um comando em linguagem natural (o próprio `operar_quadro` deste app, mas também é o padrão mais comum entre assistentes de terceiros), `montarArgumentos()` inspeciona o schema da ferramenta mapeada por nome de propriedade (`/coman|instru|mensa|message|texto|text|query|prompt/i` para o texto, `/confirm/i` para um booleano de confirmação) em vez de assumir nomes fixos — funciona tanto contra outra instância deste app quanto, na teoria, contra qualquer ferramenta MCP de terceiro que aceite instrução livre.** Extração do resultado (`extrairQuadro`/`extrairCartao`) também é best-effort: primeiro tenta o formato exato deste app (`{quadro, alterados}`), depois um objeto "parece um Cartao" solto, por fim um `cartaoId` já conhecido como último recurso — uma ferramenta remota genuinamente incompatível falha com uma mensagem clara em vez de silenciosamente inventar dados.
- **(US-072) Gotcha real descoberto testando com duas instâncias reais deste app (uma como alvo, outra como operador via MCP): `lib/visitante.ts`/`visitanteId()` (cookie por navegador) não sobrevive a uma chamada MCP.** `lib/mcp-cliente.ts` é um `fetch()` sem cookie jar (client stateless, por design — nunca guarde estado aí), então cada chamada `tools/call` que o ALVO recebe via `/mcp` cria um visitante novo e aleatório em `quadroDemoPara()`, fazendo um "criar" seguido de um "listar" (a mesmíssima ação de uma única mensagem do agente!) verem dois quadros de exemplo diferentes. Corrigido em `lib/ferramentas.ts` (não em `lib/mcp-cliente.ts`/`lib/mcp.ts`, que são compartilhados): `provedorAtual()` da ferramenta `operar_quadro` usa uma chave de visitante **fixa** (`"mcp"`) em vez de `visitanteId()` quando nem MCP nem Trello estão configurados neste app — assistentes de IA reais (Claude Desktop, ChatGPT) também não mantêm cookie entre chamadas de ferramenta, então esse é o comportamento certo mesmo fora do teste entre duas instâncias.
- **(US-072) Para rodar duas instâncias de `next dev` do mesmo app ao mesmo tempo (necessário para testar de verdade uma integração MCP entre dois papéis diferentes deste app), `PORT`/`DATA_DIR` diferentes não bastam: o Next.js 16 (Turbopack) trava um segundo `next dev` na mesma pasta de projeto ("Another next dev server is already running"), não por porta.** A saída que funcionou: `git worktree add --detach /tmp/<nome> HEAD` (checkout do commit atual em outra pasta) + `cp -Rc <repo>/agente-kanban/node_modules /tmp/<nome>/agente-kanban/node_modules` (clonefile do APFS, ~3s para 459 MB — nunca usar `ln -s` para o `node_modules`, o Turbopack recusa symlink de dependência "fora da raiz do projeto" com um erro fatal) + `rsync -a --exclude node_modules --exclude .next --exclude .git` para manter o worktree sincronizado com mudanças ainda não commitadas. Sempre `git worktree remove --force` ao terminar.
- **(US-072) `lib/mcp.ts` aplica um limite de 60 chamadas `tools/call` por minuto por código de acesso (`limiteExcedido`).** Uma única ação do agente sobre um quadro MCP pode custar 3–4 idas e voltas reais (`nomeDoCartao`/`nomeDaLista` para montar o texto do comando, a própria ação, e o `obterQuadro()` final que `lib/agente.ts` sempre busca para devolver o quadro atualizado) — em testes automatizados que disparam várias ações em sequência rápida, isso estoura o limite bem antes do humano perceberia em uso normal (uma pessoa digitando comandos um de cada vez). `lib/quadro-mcp.ts` já reduz isso com um cache de processo de 3 s (`obterQuadro`, invalidado a cada ação que muda algo) para não repetir a mesma leitura duas vezes dentro da mesma ação; gerar um novo código de acesso (`gerarCodigo()`) também reresseta o contador, útil para destravar um teste script que bateu no limite.
